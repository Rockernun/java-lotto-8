# 로또

## 기능 요구 사항(정리)
- 로또를 발행한다.
  - 구매 금액만큼의 로또를 구매한다. 
  - 1 ~ 45 사이의 숫자들 중 중복되지 않는 숫자 6개를 생성한다.
- 당첨 번호를 뽑는다.
  - 중복되지 않도록 1 ~ 45 사이의 숫자들 중 6개를 입력한다.
  - 6개의 숫자와 중복되지 않도록 보너스 번호를 입력한다.
- 당첨 결과를 발표한다.
  - 당첨 내역과 수익률을 출력한다.

 <hr />

## 입출력 요구 사항
### 입력
- 로또 구입 금액을 입력 받는다. 구입 금액은 1,000원 단위로 입력 받으며 1,000원으로 나누어 떨어지지 않는 경우 예외 처리한다.

```
14000
```

- 당첨 번호를 입력 받는다. 번호는 쉼표(,)를 기준으로 구분한다.

```
1,2,3,4,5,6
```

- 보너스 번호를 입력 받는다.

```
7
```

### 출력
- 발행한 로또 수량 및 번호를 출력한다. 로또 번호는 오름차순으로 정렬하여 보여준다.

```
8개를 구매했습니다.
[8, 21, 23, 41, 42, 43]
[3, 5, 11, 16, 32, 38]
[7, 11, 16, 35, 36, 44]
[1, 8, 11, 31, 41, 42]
[13, 14, 16, 38, 42, 45]
[7, 11, 30, 40, 42, 43]
[2, 13, 22, 32, 38, 45]
[1, 3, 5, 14, 22, 45]
```

- 당첨 내역을 출력한다.

```
3개 일치 (5,000원) - 1개
4개 일치 (50,000원) - 0개
5개 일치 (1,500,000원) - 0개
5개 일치, 보너스 볼 일치 (30,000,000원) - 0개
6개 일치 (2,000,000,000원) - 0개
```
- 수익률은 소수점 둘째 자리에서 반올림한다. (ex. 100.0%, 51.5%, 1,000,000.0%)

```
총 수익률은 62.5%입니다.
```
- 예외 상황 시 에러 문구를 출력해야 한다. 단, 에러 문구는 "[ERROR]"로 시작해야 한다.
```
[ERROR] 로또 번호는 1부터 45 사이의 숫자여야 합니다.
```

## 추가된 프로그래밍 요구 사항
- 함수 혹은 메서드의 길이가 15라인을 넘어가도록 하지 않는다.
- else 예약어와 switch/case문을 사용하지 않는다.
- Java Enum을 적용한다.
- 구현한 기능에 대한 단위 테스트를 작성한다.

# 구현할 기능 목록
### `Model(Lotto)`
- [x] 로또 한 장을 반환한다.
  - [x] 번호가 6개가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 범위 내의 숫자가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 중복된 숫자가 있으면 IllegalArgumentException 예외가 발생한다.

### `Model(Purchase)`
- [x] 금액만큼 구입 가능한 로또 매수를 계산한다.
  - [x] 구매 금액이 양수가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 구매 금액이 1,000원 단위가 아닐 경우, IllegalArgumentException 예외가 발생한다.

### `Model(LottoGenerator)`
- [x] 중복되지 않는 난수 리스트를 생성한다.
  - [x] 난수 생성 전략이 달라질 수 있으므로 추상화한다.

### `Model(Parser)`
- [x] 입력된 당첨 번호를 구분자를 기준으로 분리한다.
  - [x] 구분자가 변경될 수 있으므로 추상화한다. 
  - [x] 지정된 구분자를 기준으로 당첨 번호를 분리하는 구현체를 추가한다.
  - [x] 구분자 사이에 공백이 존재하면 IllegalArgumentException 예외가 발생한다.

### `Model(Rank)`
- [x] 당첨 가능한 등수와 당첨 금액을 저장한다.
  - [x] 번호 일치 여부에 따른 등수를 검증한다.

### `Model(WinningNumbers)`
- [x] 당첨 번호 및 보너스 번호를 저장한다.
  - [x] 당첨 번호가 양수가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 당첨 번호에 범위를 벗어난 숫자가 있다면 IllegalArgumentException 예외가 발생한다.
  - [x] 당첨 번호의 개수가 6개가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 당첨 번호에 중복된 숫자가 있다면 IllegalArgumentException 예외가 발생한다.
  - [x] 보너스 번호가 양수가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 보너스 번호에 범위를 벗어난 숫자가 있다면 IllegalArgumentException 예외가 발생한다.
  - [x] 보너스 번호가 당첨 번호와 중복된다면 IllegalArgumentException 예외가 발생한다.

### `Model(Result)`
- [x] 당첨 결과를 집계하고, 수익률을 계산한다.
  - [x] 당첨된 등수를 각각 카운트하고 검증한다.
  - [x] 당첨된 등수에 해당하는 총 상금을 바탕으로 수익률을 계산하고 검증한다.

### `Service(LottoService)`
- [x] 로또 번호와 당첨 번호를 바탕으로 당첨 여부를 판단한다.
  - [x] 구매 금액만큼의 로또를 생성한다.
  - [x] 로또 번호와 당첨 번호로 당첨 여부를 판단한다.
  - [x] 당첨된 항목에 해당하는 등수와 개수 정보를 반환한다.

### `View(InputView)`
- [x] 사용자의 입력을 받는다.
  - [x] 구매 금액을 입력받는다.
  - [x] 구매 금액이 공백이면 IllegalArgumentException 예외가 발생한다.
  - [x] 구매 금액이 숫자가 아니라면 IllegalArgumentException 예외가 발생한다.
  - [x] 당첨 번호를 입력받는다.
  - [x] 보너스 번호를 입력받는다.
  - [x] 당첨 번호와 보너스 번호가 공백이면 IllegalArgumentException 예외가 발생한다.
  - [x] 당첨 번호와 보너스 번호가 숫자가 아니라면 IllegalArgumentException 예외가 발생한다.

### `View(OutputView)`
- [x] 결과 데이터를 전달받아 출력한다.
  - [x] 몇 장의 로또를 구매했는지 출력한다.
  - [x] 각 로또의 번호들을 출력한다.
  - [x] 당첨 통계 및 수익률을 출력한다.

### `Controller(LottoController)`
- [x] 서비스 로직으로부터 데이터 및 결과를 반환받아 뷰로 출력하도록 한다.
  - [x] 입력으로부터 구매 금액을 전달 받고 서비스 로직으로 로또 생성을 요청한다.
  - [x] 입력으로부터 당첨 번호와 보너스 번호를 전달 받고 서비스 로직으로 당첨 여부 판단을 요청한다.
  - [x] 위 과정으로부터 반환받은 데이터를 뷰에게 전달한다.

# 고민한 점
- `내용`: 기본 6개의 당첨 번호(WinningNumbers)와 보너스 번호(BonusNumber)를 각각 모델로 설계했을 때, 따로 검증을 해야 했고, 서비스 로직에서 당첨 결과를 판단할 때는 전달해야 할 파라미터가 늘어나고 로직이 복잡해졌다. 
- `해결 방법`: "당첨 번호" 라는 관점에서 봤을 때, 보너스 번호도 결국 당첨 여부애 관여하기 때문에 당첨 번호(WinningNumbers)에 기존 보너스 번호(BonusNumber)를 통합하는 것이 적절하다고 생각했다. 따라서 서비스 로직에서 당첨 여부를 판단할 때, 당첨 번호(WinningNumbers)로만 판단할 수 있어서 코드가 간결해졌다. 다만, 그만큼 당첨 번호(WinningNumbers) 모델에서의 검증 로직이 길어진 부분은 향후 개선이 필요해보인다.

&nbsp;

- `내용`: 서비스 로직에서 각 당첨을 몇번 했는지 당첨 통계를 생성할 때, 기존 당첨 번호(WinningNumbers)와 로또 번호로만 결과를 도출하기에는 로직이 상당히 길어졌다.
- `해결 방법`: 당첨 결과(Result) 모델을 추가로 설계했다. 각 등수(Rank)에 따른 횟수를 값으로 저장할 수 있도록 Map 자료구조를 사용해서 당첨 횟수를 증가시키도록 처리했다. 덕분에 서비스 로직과 컨트롤러 로직도 훨씬 간결하게 작성할 수 있었다.


&nbsp;

- `내용`: 로또 번호의 범위나 번호가 양수인지, 번호의 개수가 몇개인지 검증하는 로직이 2개의 모델(Lotto, WinningNumbers)에서 중복되는 문제가 있었다. 이러한 이유로 당첨 번호(WinningNumbers)의 경우, 생성자에서 수행되는 검증 로직이 너무 길어지는 문제가 발생했다.
- `해결 방법`: 유틸리티 클래스(LottoNumbers)를 별도로 만들어서, 로또 번호와 당첨 번호(보너스 번호 제외)에서 중복되는 검증 로직(범위에 해당하는지, 번호 개수가 적절한지, 중복이 발생하는지)을 추가한 후, 각 모델의 생성자에서 검증 메서드를 통해 일괄적으로 검증하도록 처리해서 중복을 제거했다.
